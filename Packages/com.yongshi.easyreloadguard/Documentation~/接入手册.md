# Easy Reload Guard 接入手册

[README](../README.md) 说明每个特性**能做什么**。本手册说明拿到检查报告中的一条问题后，**怎么判断、怎么改、改完怎么证明**，适用于在已有工程（尤其是大量历史代码）中关闭 Domain Reload。

阅读顺序：先用第 1 节判断该谁改，再按第 2 节处理单条问题；动手前对照第 3 节的禁忌清单。大工程的推进顺序见第 5 节。

---

## 1. 先判断：这个问题该谁改

按顺序回答下面四个问题，**命中第一条就停**。

| # | 问题 | 回答“是”时的做法 |
| --- | --- | --- |
| 1 | 开启 Domain Reload、在打包后的游戏中**登出重进、切场景、重复调用 Init** 时，这个问题也会出现吗？ | **业务本身的缺陷**。修业务（订阅和取消订阅成对、Init 去重、退出流程补齐释放），不加本包特性。这类修改不算“为本包改业务”。 |
| 2 | 同一种写法在工程中出现了很多处（单例基类、事件中心、生成代码）？ | **改源头**：基类、生成模板、生成器。改一处覆盖全部派生类或生成物，不要逐个改生成物。 |
| 3 | 问题只是因为“脚本不重新加载 → 静态变量不会回到初值”？ | **加本包特性**：按第 2 节选择；特性表达不了时，写只在 Editor 编译的重置方法（第 4 节）。 |
| 4 | 代码属于第三方或外部官方包，无法修改？ | **写 Editor 适配器**：调用它自带的清理方法；没有时用 `KnownIssue` 如实报告，或用 `RequireDomainReload` 兜底。公司内部维护的包，回到包源码修复。 |

判断第 1 个问题时，看的是“上一次 Play 留下的值会不会改变下一次 Play 的结果”，而不是“有没有静态字段”。

## 2. 处理单条问题

每条字段问题下面有一行**读写位置**，来自对编译后代码的只读分析，统计的是字段在**所在类型内部**（含嵌套类型、lambda、async 方法）被读写的情况：

| 读写位置中的项 | 含义 |
| --- | --- |
| 初值 | 是否在字段初值或静态构造中赋值（下文统称“静态初始化”） |
| 初始内容 | 集合或数组是否在静态初始化中填充（集合初始化器、静态构造中的 Add） |
| 赋值 | 静态初始化以外，给字段赋值的方法 |
| 内容修改 | 静态初始化以外，修改集合元素、数组元素或调用对象方法的位置（按调用推断，可能有误差） |
| 范围 | 私有字段只能在类型内访问，结论完整；非私有字段在类型外的写入**没有分析**，需要自己搜索调用方 |
| 生成代码 | 类型标了 `[GeneratedCode]`：改生成模板 |

报告中的建议已经根据读写位置给出。下面的表格是同一套判断的完整版，用来复核建议，或者在读写位置缺失（分析失败）时自己判断。表中的 X 指报告里列出的方法。

### 2.1 静态字段的值会带到下一次 Play / 静态 Unity 对象未处理

| 读写位置 | 处理 |
| --- | --- |
| 私有，只在静态初始化时赋值或从未赋值，且没有内容修改 | 值不会变：改为 `const` 或 `static readonly`（报告中为提示） |
| 数值或 string，有初值，在 X 中修改 | 初值不是默认值 → `[ResetStatic(ResetMode.InitialValue)]`；是默认值 → `[ResetStatic]` |
| 数值或 string，没有初值，在 X 中赋值 | `[ResetStatic]` |
| 引用，没有初值，在 X 中赋值 | 确认下一次 Play 会再经过 X（Awake、Init、判空创建）→ `[ResetStatic]` |
| 引用，有初值，在 X 中重新赋值 | 只有下一次 Play **一定先**经过 X 时才能用 `[ResetStatic]`；否则写重置方法恢复初值 |
| 引用，只有初值、没有其他赋值 | **不能置 null**（没有地方会重建它）。对象在下一次 Play 仍然有效（持久资产、无状态服务）→ `[ReloadSafe("原因")]`；对象内部有 Play 中的状态 → 在重置方法里重新创建 |
| 非私有，类型内没有赋值 | 搜索类型外的赋值方，再按上面几行判断 |

### 2.2 只读集合、数组或对象的内容会带到下一次 Play

| 读写位置 | 处理 |
| --- | --- |
| 只在静态初始化时填充，之后不修改 | **不要 Clear**（静态构造不会再执行，清空后永久为空）。内容确定不变 → `[ReloadSafe("原因")]` |
| 没有初始内容，在 X 中追加或删除 | `[ResetStatic(ResetMode.Clear)]` |
| 既有初始内容，又在 X 中修改 | Clear 会丢掉初始内容：写重置方法，清掉 Play 中加入的数据并恢复初始内容 |
| 数组元素在 X 中被改写 | 在重置方法中恢复元素 |
| 对象（缓存、对象池、注册表）在 X 中被调用 | 看对象自己有没有重置方法：有 → 在重置方法里调用它；只是纯计算缓存 → `[ReloadSafe]` |

### 2.3 静态事件或委托未处理

1. 找到所有订阅方（`+=` 的位置）。订阅方是会被销毁的对象（MonoBehaviour、System、View 等）时，它应在自己销毁或退出时成对 `-=`。缺少取消订阅时，按第 1 节问题 1 处理：**这是业务缺陷**。
2. 订阅方都成对取消之后，再在事件字段上加 `[field: ResetStatic]`，进入 Play 时清掉异常退出留下的订阅。
3. 不能清空的情况：订阅只在静态构造或 `[InitializeOnLoad]` 中登记一次（清掉后不会再登记）。

### 2.4 async void 方法 / 静态字段持有异步任务、线程或计时器

由发起任务的业务代码负责取消，写法见 README 第 3 节“异步任务”。只把字段置 null 不会停止已在运行的工作。

### 2.5 已加的特性需要复查

- **已加的重置会破坏下一次 Play**：已经写下的 `[ResetStatic]` 会让下一次 Play 出错，例如把只在静态初始化中创建的引用置 null，或者把静态初始化中填好的集合 Clear 掉。按 2.1、2.2 的表格改写。确认类型外会在下一次 Play 重新赋值时，可以记为已知遗留。
- **重置方法漏掉了字段**：类型有 `[ResetMethod]`，但重置方法（含它调用的类型内方法）没有处理某个字段。要么在重置方法里恢复它，要么加 `[ReloadSafe("原因")]` 说明为什么保留。不要只写一个处理局部字段的 Clear 方法，让整个类型被当作“已处理”。
- **声明保留的字段仍在 Play 中被修改**：`[ReloadSafe]` 只在写下时确认过。字段之后仍在静态初始化以外被赋值或修改内容时，报告会列出修改的位置和当初写的原因。逐条确认：
  - 保留下来的值在下一次 Play 仍然正确（纯计算缓存、编辑器偏好、由同一段代码成对维护的计数）→ 记为已知遗留；
  - 原因已经不成立 → 去掉 `[ReloadSafe]`，按 2.1、2.2 改用重置。

  遗留清单会记下当时的修改位置。之后有人新增或删除了修改的地方，这一行会失效，需要重新确认，不要直接重新生成清单了事。

## 3. 禁忌清单

| 不要这样做 | 原因 | 改为 |
| --- | --- | --- |
| 对只在静态构造中填充的目录或查找表用 `Clear` | 静态构造不会再执行，清空后永久为空 | `[ReloadSafe]` |
| 对有初值、没有地方重建的引用用 `[ResetStatic]` | 下一次 Play 拿到 null | 在重置方法中重新创建，或 `[ReloadSafe]` |
| 只把对象的引用置空，不处理它登记到别处的监听或回调 | 旧监听仍在全局表中，每次 Play 都多一份 | 监听表和对象引用在同一处重置；更好的做法是对象销毁时自己注销 |
| 把字段置 null 当作停止线程、计时器、下载或 Socket | 已在运行的工作不会因此停止 | 调用业务的停止或取消方法 |
| 用类型级、程序集级 `[ReloadSafe]` 或整批记为已知遗留来掩盖未确认的问题 | 之后新出现的问题也会被一起忽略 | 逐个字段说明原因；遗留清单只放确认过的问题 |
| 为本包在业务中加登记调用、判断分支、参数或 Unity 消息 | 改变了业务流程和打包后的行为 | 用特性、只在 Editor 编译的重置方法或适配器 |
| 新增 `[OnExitPlayMode]` 方法来释放订阅、线程或资源 | 这些释放在打包后的游戏中同样需要，缺少是业务缺陷 | 补齐业务的销毁或退出流程，再给已有的停止方法加特性 |
| 手改生成物 | 下次生成会被覆盖 | 改模板或生成器 |
| 只因读写位置写着“赋值：静态初始化以外没有”，就把非私有字段改成 readonly | 类型外可能有写入（包括反射写入） | 先搜索调用方 |

## 4. 只在 Editor 编译的重置方法

业务类型没有现成的重置方法、特性又表达不了时（需要恢复初始内容、几个字段需要一起恢复、需要重新填充只读表），可以在该类型中新增一个只在 Editor 编译的重置方法：

```csharp
public static class ConditionRegistry
{
    static readonly Dictionary<int, List<Action>> s_Listeners = new Dictionary<int, List<Action>>();
    static readonly Dictionary<int, string> s_Names = BuildNames();   // 只在静态初始化中填充
    static int s_Version = 1;

    public static void Listen(int id, Action listener) { /* 业务代码不变 */ }

#if UNITY_EDITOR
    [EasyReloadGuard.ResetMethod]
    static void ResetForPlay()
    {
        s_Listeners.Clear();   // Play 中加入的数据
        s_Version = 1;         // 恢复初值
        // s_Names 内容不变，不处理；检查器会报告“重置方法漏掉了字段”，给它加 [ReloadSafe("只读名称表")] 说明
    }
#endif
}
```

规则：

1. 方法连同特性整体放在 `#if UNITY_EDITOR` 中，打包后的游戏中不存在这个方法。方法必须是 `static`、无参、返回 `void`、同步，并且可以重复调用。
2. 只把**本类型**的静态字段恢复成“脚本刚加载、第一次进入 Play 时”的样子：初值、空集合、重新填充只读表。不调用业务流程（不 Init、不创建 GameObject、不订阅事件、不派发事件）。
3. 业务代码不调用它，只由本包在进入 Play 时调用。
4. 类型中每个会变的静态字段，要么由它处理，要么加 `[ReloadSafe]`；检查器会逐个核对。
5. 停止 Play 时的释放不适用本节：`[OnExitPlayMode]` 只能加在业务已有的方法上（见第 3 节）。

## 5. 大工程的推进顺序

不要逐条处理全部报告。几千条问题里，大部分是常量式字段、只读目录、第三方包和生成代码。

1. **运行检查**，先看报告中的“按类型汇总”：按来源 → 程序集 → 类型分组，Assets 源码在前、问题多的类型在前。一个类型的静态状态通常由同一段代码负责，可以按行分工。
2. **先清掉简单的**：提示级的“改为 const 或 static readonly”、只在静态初始化时填充的只读目录，可以批量处理，也可以保持提示不动；生成代码改模板。
3. **统一写法**：把随手写的单例、事件中心、管理器收敛到少数几种基类或写法，在基类上加一次特性。这是处理大量随手代码最省力的方式。
4. **按第 1 节逐个类型处理**：业务缺陷修业务，只因脚本不重新加载才出现的问题加特性。
5. **记录剩余问题**：确认过的问题记为已知遗留，把“进入 Play 前检查”设为“阻止进入 Play”，阻止新问题进入。
6. **尽早实际运行**：关闭 Domain Reload、开启 Scene Reload，连续 Play → Stop 至少 3 次。每次停止后，本包会自动检查并写入 `Library/EasyReloadGuard/ResidueReport.md`：
   - **仍引用已销毁的对象**：静态字段或回调仍指向上一次 Play 销毁的对象 → 负责的代码没有清理或取消订阅。
   - **比上次停止时增加**：同一个回调方法在引擎/编辑器事件或项目委托中的次数每次都在增加，或者集合元素每次都在增加 → 重复订阅或只加不删。报告给出方法全名，可以直接找到负责的代码（例如第三方包在 `EditorApplication.playModeStateChanged` 上每次都多订阅一组）。
   - 只创建集合、字符串、数值的静态构造照常读取；其他有静态构造的项目类型默认不读取（读取会触发尚未执行的静态构造）。跳过和无法读取的数量见报告，需要时在设置中打开“停止后检查也读取有静态构造的类型”。

   让实际运行的结果决定下一步先处理什么，比继续扩大静态清单更省力。

## 6. 交付时要给出的证据

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 编译通过、检查报告中的问题数量下降 | 特性被识别；没有新增“特性用法错误”“已加的重置会破坏下一次 Play”“重置方法漏掉了字段” | 运行时行为正确 |
| EditMode 测试通过 | 本包和案例的单元行为 | 业务工程连续 Play 的结果 |
| 连续 Play → Stop，停止后检查没有新增问题 | 实际走过的流程中没有残留 | 没走到的入口（登出重进、加载中途停止等需要单独走） |

静态检查、编译、测试、实际运行分别报告；没有运行的项目标为未验证。
